# 이미지 로딩 최적화 작업 기록

**작업일**: 2026-08-10 ~ 2026-08-11
**배경**: 사진 로딩이 너무 느리다는 문제로 시작. 확인해보니 원인은 CDN이 아니라(GitHub Pages는 이미 Fastly CDN으로 서빙됨) **이미지 자체가 과도하게 큼** — 원본 해상도 그대로, 압축 없이 올라가 있었음.

## 요약

| 단계 | 내용 | 효과 |
|---|---|---|
| 1. WebP 변환 | 사진 114개 jpg/png → WebP | 111MB → 35MB (-68%) |
| 2. 리사이즈 | 실제 표시 크기에 맞춰 81개 갤러리 사진 축소 | 20MB → 11.6MB (해당 사진 기준, 추가 -42%) |
| 3. 투어 독 썸네일 | 360° 뷰어 하단 장면 목록이 전체 파노라마를 썸네일로 재사용하던 것을 실제 썸네일로 교체 | 투어 첫 로딩 14.9MB → 0.8MB (-95%) |
| 4. 투어 파노라마 교체 (08-11) | 사용자가 씬 28개를 새로 촬영한 원본 jpg/png(32개)로 직접 교체, 파이프라인 재적용 | `tour/images/` jpg 원본 29.3MB → webp 17.5MB, 썸네일 0.46MB 재생성 |

**최종 상태**: `images/` 11MB, `tour/images/` 17MB(파노라마 32장, 의도적으로 고해상도 유지) + `tour/images/thumb/` 0.52MB(썸네일 32장).

## 1. WebP 변환

- 대상: `images/`, `images/docs/`, `images/food/`, `tour/images/` 아래 jpg/png 114개
- 제외: `favicon.png`, `apple-touch-icon.png` (브라우저/OS 호환용, PNG 유지 필요)
- 품질: 사진 quality=82, 투명배경(로고) quality=90, `method=6`(최고 압축)
- HTML 14개 파일 + `assets/style.css` + `assets/app.js`의 이미지 경로를 전부 `.webp`로 갱신
- 원본 jpg/png는 git으로 삭제(히스토리에는 남아있어 필요시 복구 가능)

**결과**: 111MB → 35MB (-68%)

## 2. 리사이즈

WebP 변환만으로는 부족했음 — 예를 들어 `p001.jpg`는 1733×2600 원본 그대로였는데, 실제 화면에는 갤러리 썸네일(최대 표시 폭 ~717~760px)로만 노출됨. 압축은 됐지만 픽셀 수 자체가 화면에 필요한 양보다 훨씬 많았음.

- 리티나(2배) 디스플레이 기준 안전한 상한선으로 **최대 변 1600px** 캡 적용
- 화질 저하를 막기 위해, 이미 압축된 webp를 다시 압축하는 대신 **git 히스토리의 원본(webp 변환 전 jpg)에서 직접 리사이즈+재인코딩**
- 360° 투어 파노라마(`tour/images/*.webp`)는 **의도적으로 제외** — 뷰어에서 확대해서 보기 때문에 축소하면 확대 시 흐려짐
- award, docs, food, logo 이미지는 이미 표시 크기에 맞아 그대로 둠

**결과**: 대상 81개 파일 기준 20MB → 11.6MB, 페이지 기준 index.html 11.5MB→6.2MB, facilities.html 14.8MB→7.6MB

## 3. 360° 투어 갤러리 독 썸네일

`tour/tour.html`의 pannellum 360° 뷰어는 원래도 "현재 씬만 로드, 핫스팟으로 이동한 씬만 추가 로드"하는 지연 로딩을 기본 지원함. 하지만 하단 장면 목록(독)의 썸네일이 **화면엔 120×68px로만 보이면서 실제로는 4096×2048 원본 파노라마 파일(300KB~1.4MB)을 그대로 재사용**하고 있어서, 페이지를 열자마자 28개 씬 전부가 로드되고 있었음.

- `tour/images/thumb/`에 480px 폭의 진짜 썸네일 28장(평균 ~14KB) 생성
- `buildGallery()`가 독 썸네일은 `thumb/`, 뷰어 본체는 원본 파노라마를 쓰도록 분리

**결과** (네트워크 트레이스로 확인):
- 최초 로딩: 파노라마 1장(현재 씬) + 썸네일 28장 = 0.79MB (기존 14.91MB)
- 핫스팟으로 다른 씬 이동 시: 그 씬 1장만 추가 로드 (씬당 +0.3~0.7MB)

## 4. 투어 파노라마 교체 (2026-08-11)

사용자가 촬영 결과물이 바뀌었다며 `tour/images/`의 파노라마 28장을 로컬에서 새 jpg/png 32장(여탕/남탕/찜질방 재촬영 + 소금방·아이스방 등 4개 씬 추가)으로 직접 교체하고 `tour.html`의 `SCENES` 배열도 새 씬 구성에 맞게 수정해둔 상태였음. 이 시점에서 `tour.html`의 독 썸네일 로직도 `img.src=s.image.replace('images/','images/thumb/')`(3단계에서 만든 최적화)에서 `img.src=s.image`(원본 파노라마를 썸네일로 재사용)로 되돌아가 있었음 — 즉 3단계에서 고친 문제가 새 사진과 함께 재발한 상태.

그대로 커밋하지 않고 기존 파이프라인을 새 사진에 재적용:

1. `scripts/convert_to_webp.py` — 새 jpg/png 32장 + logo/brandmark를 webp로 변환 (29.3MB → 17.5MB, -40%)
2. `tour/images/thumb/` 삭제 후 `scripts/make_tour_thumbs.py` 재실행 — 32장 재생성 (0.46MB)
3. `scripts/update_refs.py` — `tour.html`의 `.jpg`/`.png` 참조를 `.webp`로 일괄 치환
4. `buildGallery()`의 썸네일 소스를 다시 `images/thumb/`로 되돌림(`img.src=s.image` → `img.src=s.image.replace('images/','images/thumb/')`, `decoding='async'` 복원)
5. 원본 jpg/png 삭제 (git 히스토리에 남음)
6. Playwright로 실제 페이지 열어서 검증: 첫 씬(`여탕_전경`) 파노라마 정상 로드, 독 썸네일 32장 렌더링, 썸네일 클릭 시 다른 씬(`여탕_중온사우나`)으로 정상 이동, 콘솔 에러·실패한 요청 없음

**교훈**: 사진을 파일시스템에서 직접 교체하는 경우 최적화 파이프라인(webp 변환, 썸네일 재생성, 참조 갱신)을 거치지 않기 쉬움 — `tour.html`처럼 `buildGallery()`가 `thumb/` 경로를 참조하도록 짜여 있어도, 이미지 자체나 그 로직 줄이 되돌려지면 3단계에서 고친 "독 썸네일이 원본 파노라마를 재사용하는" 문제가 조용히 재발할 수 있음. 새 사진이 들어올 때마다 이 문서의 "새 사진을 추가할 때" 절차를 그대로 따를 것.

## 부수적으로 발견·수정한 버그

`assets/app.js`(모든 페이지 공용, 홈 히어로 배경을 JS로 교체하는 로직)에 `.jpg` 확장자가 하드코딩되어 있던 걸 놓쳤다가, 브라우저(Playwright) 실측 검증 중 404를 발견해서 수정함. HTML/CSS만 훑고 JS 파일을 안 보면 놓치기 쉬운 케이스였음 — 이미지 경로를 바꿀 땐 `.js` 파일도 반드시 같이 검색해야 함.

## 새 사진을 추가할 때

`scripts/` 아래에 재사용 가능한 스크립트를 남겨둠:

| 스크립트 | 용도 |
|---|---|
| `scripts/convert_to_webp.py` | `images/`, `images/docs/`, `images/food/`, `tour/images/`의 새 jpg/png를 webp로 변환 |
| `scripts/resize_to_webp.py` | 갤러리 사진을 1600px 상한으로 리사이즈(git 히스토리 원본 필요) |
| `scripts/make_tour_thumbs.py` | 투어 파노라마용 480px 독 썸네일 생성 |
| `scripts/update_refs.py` | HTML/CSS의 이미지 참조를 일괄 `.webp`로 치환 |

새 사진을 추가한다면: 원본을 해당 폴더에 넣기 → `convert_to_webp.py` 실행 → HTML에 `<img src="....webp">`로 등록 → **`assets/app.js`에 해당 사진을 하드코딩 참조하는 곳이 있는지도 확인**.
